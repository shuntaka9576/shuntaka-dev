# 記事一覧へのタグ絞り込みUIの追加（apps/web）

- 起票日: 2026-07-05
- 関連: [記事タグ機能（最大3階層）の追加と既存記事へのタグ付与](../2026-07-05-article-tags/index.md)
- ステータス: 実装完了・ローカル検証済み（Phase D の dev E2E と Phase E の本番反映が残り）。クライアントサイドフィルタは [タグ絞り込みのサーバーサイド化 Phase F](../2026-07-05-server-side-tag-filter/index.md) により API 駆動方式に置き換え済み

## 起票理由

blog-api 側で記事タグ機能（最大3階層）を実装し、一覧・詳細 API のレスポンスに `tags: string[]`（`tech/aws/lambda` 形式のフルパス）が含まれるようになった。フロントエンド表示は同タスクのスコープ外だったため、本タスクで apps/web の記事一覧にタグ絞り込み UI を追加する。

shuntaka.dev はタイトルと日付のみの一覧を軸にしたミニマルなデザインであり、これを壊さないことを最優先とする。デフォルト状態では現状の見た目を一切変えず、絞り込みは段階的開示（progressive disclosure）で提供する。

## 前提

- 一覧 API（`GET /users/shuntaka/articles?type=tech|note`）と詳細 API のレスポンスに `tags` が含まれていること（blog-api Phase F/G 完了）
- 記事数は全 111 件規模。一覧 API が type 単位で全件返せる前提でクライアントサイドフィルタを採用する（後述の論点参照）

## 設計方針

| 論点               | 決定                                                                                                                                                                                                                                                                                                                          |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| デフォルト表示     | 現状と完全に同一。タブ行の右端に「タグ」トグル（tag アイコン + テキスト、13px、muted）を置くのみ。使わない読者には何も増えない                                                                                                                                                                                                |
| タブとルートの対応 | tech タブ → `tech/*`、note タブ → `misc/*` のタグのみ表示。ルート階層は UI に出さない（タブが代替するため）。表示・URL とも root プレフィックスを省略した相対パス（`rust`、`aws/lambda`）を用いる                                                                                                                             |
| タグパネル         | トグルクリックで一覧上部にインライン展開（モーダル・ドロワーは使わない）。タグはモノクロのテキストピル + 記事数。色ラベルは導入しない                                                                                                                                                                                         |
| aws の3階層目      | `aws` ピル自体はクリックで選択可能（祖先マッチ）。隣のシェブロンで `/lambda` `/cdk` 等の子タグをインライン展開。展開時は親 + 子を1つの枠（セグメントグループ）に収めて他のタグと混ざらないようにする（実装時に変更）。選択中の子タグがあればパネルを開いた時点で親を自動展開。展開状態はローカル state のみ（URL に載せない） |
| AND / OR           | 選択タグが2つ以上のときだけトグルを表示。デフォルトは AND（実装時に変更。ファセット表示と組み合わせて絞り込み体験を優先）。「すべてのタグを含む記事 / いずれかのタグを含む記事」の説明文を併記する                                                                                                                            |
| マッチング         | 祖先マッチ。選択タグ `t` に対し、記事タグ `pt` が `pt === t \|\| pt.startsWith(t + "/")` なら一致。`aws` 選択で `aws/lambda` の記事もヒットする                                                                                                                                                                               |
| 選択中バー         | パネルを閉じても選択状態が見えるよう、タブ直下に「rust × AND aws ×」形式のチップ行 + ヒット件数を表示。チップの × で個別解除                                                                                                                                                                                                  |
| 記事行の表示       | 通常時はタイトル + 日付のまま。絞り込み中のみ、日付の横に `#rust` 形式でタグを muted 表示し、マッチしたタグだけ text-primary で強調                                                                                                                                                                                           |
| 0件時              | 「一致する記事がありません — OR に切り替えるかタグを外してください」。ファセット表示により UI 経由では原則発生しないが、直リンクで発生し得るため導線を維持する                                                                                                                                                                |
| URL 同期           | `?tags=rust,aws%2Flambda&mode=or` を searchParams に同期。共有可能・ブラウザバック対応。`mode` は2タグ以上かつ OR のときのみ付与、デフォルト（and）時は省略                                                                                                                                                                   |
| 絞り込みの実装     | クライアントサイドフィルタ。一覧 API の `tags` を使い、絞り込み API は作らない（スコープ外）                                                                                                                                                                                                                                  |
| タグ件数           | 取得済み記事配列からクライアント側で集計（祖先タグは配下の件数を合算）。件数降順でピルを並べる。絞り込み中（AND）はヒット集合と組み合わせられるタグのみ表示（ファセット。0件になる組み合わせを選べなくする）。OR は選択で結果が広がるため全タグを表示                                                                         |
| タグの出所         | タグ一覧も記事配列から導出する（`tags` 一覧 API は作らない）。記事に1件も付いていないタグは UI に出ない仕様で問題ない                                                                                                                                                                                                         |
| アクセシビリティ   | タグピルは `<button aria-pressed>`、パネルトグルは `aria-expanded`。キーボード操作のみで選択・解除・モード切替が完結すること                                                                                                                                                                                                  |

## UI 仕様

### 状態遷移

```
[初期状態]
  タイトル / タブ / 一覧（現状どおり）+ タブ行右端に「タグ」トグル
    │ トグルクリック
    ▼
[パネル展開]
  タグピル一覧（件数付き、件数降順）
    │ タグ選択（1つ）
    ▼
[絞り込み中・単一]
  選択中バー表示、一覧がフィルタされる。AND/OR は出さない
    │ タグ選択（2つ目）
    ▼
[絞り込み中・複数]
  AND/OR トグル + 説明文が出現。選択中バーのチップ間に演算子を表示
```

- タブ切り替え時は選択タグ・mode をリセットする（tech のタグは note に存在しないため持ち越し不可）
- パネル開閉と選択状態は独立。パネルを閉じても絞り込みは維持される（選択中バーが残るため状態は見失わない）

### コンポーネント構成（実装済み）

一覧本体はサーバーレンダリングのまま維持し、絞り込み UI をクライアントアイランドとして差し込む構造。状態は `TagFilterProvider`（Context）が一元管理する。

```
ArticleListView                    … Server Component。perPage=all で全件 fetch、既定表示のページスライスもここで実施
  └ TagFilterProvider              … "use client"。選択タグ / mode / パネル開閉の状態と URL 同期を持つ Context Provider
      └ BaseLayout                 … typeHeaderEnd スロットに TagFilterHeaderToggle を配置
          ├ TagFilterHeaderToggle  … タブ行右端のトグル（アイランド。TagFilterToggle を Context に接続）
          ├ TagFilterControls      … パネル + 選択中バーのアイランド（TagFilterPanel / ActiveTagBar を Context に接続）
          └ FilteredArticleList    … 絞り込みなしはサーバーレンダリング済み children をそのまま表示し、
                                      絞り込み中だけクライアント側でヒット記事（ArticleCard + tags 表示)に差し替える
```

- URL 同期は `useSearchParams` ではなく **`history.pushState` / `popstate` によるシャローナビゲーション**で行う。タグの追加・削除・クリアは pushState（戻るで1段階ずつ戻れる）、mode 切替のみ replaceState
- SSR は常に絞り込みなしで描画（静的 HTML は現行と同一構造）。直リンク時はマウント後の effect で URL から選択状態を復元する（復元まで一瞬デフォルト一覧が見える）
- `/page/N` で絞り込みを開始すると URL は `/?tags=...` に移り、選択をすべて外すと `/page/N` に戻る（表示スライスとの整合を保つ）
- フィルタ・件数集計は `useMemo`（111件規模）
- トグルのラベルは DESIGN.md の「nav ラベルは小文字」ルールに合わせ `tags`（タグアイコンは Lucide 相当の stroke 1.5px インライン SVG）

### ハイドレーション問題と loading.tsx の削除（実装時の知見）

一覧ページ（`/`、`/type/note`）の `loading.tsx` は本タスクで削除した。経緯:

- 一覧をクライアントコンポーネント経由で描画する構成にしたところ、プリレンダリング HTML が「loading.tsx のスケルトン + 後追いコンテンツ + インライン swap スクリプト」というストリーミング形に変わるケースがあった（クライアントアイランドの構成次第で発生し、閾値的で制御不能）
- このストリーミング形の静的 HTML は、`next start` でのハイドレーション時にページ全体を包む Suspense 境界が **PENDING のまま解決されず**、ページが一切インタラクティブにならない（テーマトグルすら効かない）。コンソールエラーなし。React fiber を直接確認して特定
- `loading.tsx`（= ルートセグメントの Suspense fallback）を削除すると、ストリーミング形になる余地がなくなり、常に単一形（旧来と同じ構造）の HTML が生成されて問題が根治する
- タブ切り替え時のスケルトンは失われるが、ナビゲーション中のフィードバックは既存の NProgress バーが担っているため UX 上の実害は小さいと判断。記事詳細（`[userName]/articles/[slug]/loading.tsx`）は別セグメントで問題が再現しなかったため残置
- `useSearchParams` + Suspense boundary の構成も同じストリーミング形を誘発するため不採用（URL 同期は pushState で実装)

### フィルタロジック（擬似コード）

```ts
const hit = (sel: string, postTags: string[]) =>
  postTags.some((pt) => pt === sel || pt.startsWith(sel + '/'));

const matches = (post: Article) =>
  selected.length === 0 ||
  (mode === 'and'
    ? selected.every((s) => hit(s, post.relativeTags))
    : selected.some((s) => hit(s, post.relativeTags)));
```

- `relativeTags` は API の `tags` から現在タブの root プレフィックス（`tech/` or `misc/`）を除去したもの。root が一致しないタグ（tech 記事に misc タグが付くケース）は除去せずフルパスのまま扱い、UI には出さない

## Phase D: 検証手順

dev 環境（blog_dev のタグ backfill 適用済み）で以下を確認する。

1. デフォルト表示が現行とピクセル単位で変わらないこと（タグトグルの追加を除く）
2. `rust` 単一選択で該当記事のみ表示、AND/OR トグルが出ないこと
3. `rust` + `aws` の2タグで AND/OR トグルが出現（デフォルト AND）し、切り替えで件数が変わること
4. `aws` 選択で `aws/lambda` タグの記事（リアーキ記事等）がヒットすること（祖先マッチ）
5. タグ選択中はヒット集合と組み合わせられるタグだけがパネルに表示されること（ファセット）。共起しない2タグの直リンクで0件にした際、空状態メッセージと OR への導線が出ること
6. `?tags=rust,aws&mode=or` の直リンクで絞り込み済み状態が復元されること
7. タブ切り替えで選択がリセットされ、URL からも `tags` / `mode` が消えること
8. キーボードのみで タグ選択 → mode 切替 → 個別解除 → クリア が完結すること
9. Lighthouse でパフォーマンス・アクセシビリティのスコアが現行から劣化していないこと

## 論点・保留

- **ページネーション**: 現状の一覧 API が type 単位で全件返す前提。将来ページネーションを入れる場合、クライアントサイドフィルタは成立しなくなるため、その時点でタグ絞り込み API（`?tags=` パラメータ）+ ファセットカウント API の追加を検討する。本タスクでは対応しない → [タグ絞り込みのサーバーサイド化（50万記事スケール対応）](../2026-07-05-server-side-tag-filter/index.md) として起票済み
- **タグ個別ページ**（`/tags/rust` のような SSG ページ）: SEO 上は有効だが本タスクのスコープ外。URL 同期のクエリ形式は将来これと共存できる（別ルートのため衝突しない）
- **記事詳細ページのタグ表示**: 詳細 API にも `tags` は含まれるが、詳細ページの表示とタグクリックでの一覧遷移は別タスクとする

## スコープ外

- タグ絞り込み API・ファセットカウント API（クライアントサイドで完結させる）
- タグ個別ページ（/tags/\*）
- 記事詳細ページへのタグ表示
- note ↔ tech を横断した絞り込み（タブ = ルートの対応を崩すため）
